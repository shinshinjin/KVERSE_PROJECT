# KVERSE Metaverse Prototype

> Unity 기반 메타버스 프로토타입 개발 Case Study  
> 원본 소스코드와 에셋은 공개하지 않고, 제가 맡았던 구현 범위와 작업 내용을 중심으로 정리했습니다.

<br />

## 1. 프로젝트 개요

**KVERSE Metaverse Prototype**은 3D 월드 안에서 캐릭터를 조작하고, 아바타 외형을 커스터마이징할 수 있도록 만든 메타버스 프로토타입입니다.

입사 초기 참여했던 프로젝트로, 당시에는 Unity 실무 프로젝트 구조를 익히면서 실제 기능 구현을 맡아 진행했습니다.

맵 자체는 3D 디자이너가 제작한 상태였고, 저는 그 월드 안에서 플레이어가 이동하고 카메라가 따라가며, UI를 통해 로그인 화면에서 인게임으로 넘어가고, 캐릭터 외형을 바꾸는 흐름을 구현했습니다.

전체 흐름은 다음과 같습니다.

    로그인 화면
    → 인게임 진입
    → 캐릭터 이동 및 카메라 조작
    → 커스터마이징 화면 진입
    → 아바타 파츠 선택
    → 선택 결과 반영
    → 다시 인게임으로 복귀

<br />

## 2. 개발 목적

이 프로젝트의 목적은 메타버스 서비스에서 기본적으로 필요한 플레이 흐름을 프로토타입 단계에서 확인하는 것이었습니다.

특히 제가 맡은 부분에서는 다음 흐름이 자연스럽게 이어지는지를 중점적으로 봤습니다.

- 로그인 화면에서 인게임 화면으로 넘어가는 흐름
- 인게임에서 캐릭터를 이동시키고 카메라를 조작하는 흐름
- 커스터마이징 화면으로 진입하고 다시 돌아오는 흐름
- 선택한 아바타 파츠가 실제 캐릭터에 반영되는 흐름
- UI 버튼과 캐릭터, 카메라, 화면 상태가 서로 맞게 동작하는지 확인

입사 초기 프로젝트였기 때문에 거대한 시스템을 처음부터 설계했다기보다는, 이미 만들어진 리소스와 화면 구조 안에서 실제 플레이 가능한 흐름을 연결하는 작업에 가까웠습니다.

<br />

## 3. 담당 역할

제가 맡은 작업은 크게 네 가지였습니다.

### 캐릭터 이동 및 카메라

- 인게임 캐릭터 이동 처리
- 카메라 방향 기준 이동 흐름 구성
- 마우스 입력을 통한 시점 조작
- 캐릭터 이동, 회전, 점프 등 기본 조작 확인
- 인게임 상태와 커스터마이징 상태에 따라 조작 가능 여부 처리

### 캐릭터 커스터마이징

- 아바타 외형 파츠 변경 기능 구현
- 의상, 헤어, 바디 등 파츠 데이터를 분류해 관리
- 선택한 파츠를 캐릭터에 반영
- 커스터마이징용 아바타와 인게임 아바타의 외형이 맞도록 처리
- 의상 변경 시 겹쳐 보이는 바디 파츠를 숨기거나 다시 보이게 처리

### UI 상호작용

- 버튼 클릭에 따른 화면 전환 처리
- 커스터마이징 UI 진입/복귀 흐름 구현
- 커스터마이징 모드에 따라 카메라와 UI 상태 전환
- 인게임 UI와 커스터마이징 UI가 동시에 보이지 않도록 상태 관리

### 로그인 → 인게임 흐름

- 로그인 화면에서 인게임 화면으로 넘어가는 흐름 구성
- 로딩 또는 화면 전환용 프리팹 연결
- 씬 전환과 UI 전환이 어색하지 않도록 흐름 정리

<br />

## 4. 주요 구현 내용

### 4-1. 캐릭터 이동 및 카메라

인게임에서는 플레이어가 캐릭터를 직접 조작하며 월드를 둘러볼 수 있어야 했습니다.

맵은 이미 제작되어 있었기 때문에, 제가 신경 쓴 부분은 월드 제작보다는 그 안에서 캐릭터가 자연스럽게 움직이고 카메라가 따라가는 기본 조작감이었습니다.

구현한 내용은 다음과 같습니다.

- 키 입력 기반 캐릭터 이동
- 카메라 방향을 기준으로 한 이동 방향 처리
- 마우스 입력을 통한 시점 회전
- 점프 및 기본 이동값 조정
- 커스터마이징 화면 진입 시 이동/점프 제한
- 인게임 복귀 시 조작값 복원

처음에는 캐릭터만 움직이면 된다고 생각하기 쉬웠지만, 실제로는 카메라 방향과 캐릭터 이동 방향이 맞지 않으면 조작감이 바로 어색해졌습니다.

그래서 입력, 캐릭터 회전, 카메라 시점을 같이 보면서 조정했습니다.

<br />

### 4-2. 캐릭터 커스터마이징

커스터마이징은 아바타의 외형 파츠를 선택하고, 선택 결과를 캐릭터에 반영하는 기능입니다.

프로젝트에는 의상과 외형 파츠가 여러 개 있었기 때문에, 버튼마다 직접 프리팹을 하나씩 연결하는 방식으로는 관리가 어려웠습니다.  
그래서 파츠 정보를 데이터로 분리해서 관리하는 방식이 필요했습니다.

이때 사용한 방식이 `ScriptableObject` 기반 아이템 데이터 구조였습니다.

각 아이템 데이터에는 다음과 같은 정보가 들어가도록 구성했습니다.

- 아이템 ID
- 아이템 이름
- 아이템 카테고리
- 착용 타입
- 적용 대상 파츠
- 아이콘
- 실제 적용할 메시 렌더러
- 해당 아이템 착용 시 숨겨야 하는 바디 파츠 목록

이렇게 정리해두면 UI에서는 아이템 목록을 가져와 보여주고, 캐릭터 쪽에서는 선택된 데이터에 따라 실제 외형을 바꾸는 식으로 역할을 나눌 수 있습니다.

당시에는 이 구조가 처음부터 완벽하게 잡혀 있었다기보다는, 의상 종류가 늘어나면서 관리가 어려워지는 부분을 줄이기 위해 데이터 형태로 정리해나간 쪽에 가까웠습니다.

<br />

### 4-3. 의상 교체와 바디 파츠 처리

커스터마이징에서 단순히 옷 모델만 바꾸면 끝나는 줄 알았지만, 실제로는 의상과 몸 파츠가 겹쳐 보이는 문제가 있었습니다.

예를 들어 상의를 바꾸면 팔이나 어깨 일부가 옷 밖으로 튀어나와 보일 수 있고, 하의를 바꾸면 다리나 양말 파츠가 겹칠 수 있습니다.

그래서 의상 변경 시에는 메시를 바꾸는 것과 함께, 필요 없는 바디 파츠를 숨기는 처리를 같이 했습니다.

작업 방향은 다음과 같았습니다.

- 선택한 의상 메시를 캐릭터에 적용
- 커스터마이징 화면의 아바타와 인게임 아바타에 같은 결과 반영
- 의상 종류에 따라 일부 바디 파츠를 숨김 처리
- 기본 아바타 상태로 되돌리는 초기화 흐름 구성

이 작업을 하면서 캐릭터 커스터마이징은 단순히 “옷을 갈아입히는 기능”이 아니라, 파츠끼리 어떻게 겹치고 연결되는지 계속 확인해야 하는 작업이라는 걸 알게 됐습니다.

<br />

### 4-4. UI 상호작용 및 화면 전환

커스터마이징 화면은 인게임 화면과 분리된 상태로 동작하도록 구성했습니다.

사용자가 커스터마이징에 들어가면 캐릭터가 움직이면 안 되기 때문에, 이동과 점프 값을 막고 커스터마이징 UI와 전용 카메라를 활성화했습니다.  
반대로 인게임으로 돌아오면 UI를 닫고 캐릭터 조작을 다시 복원했습니다.

흐름은 다음과 같습니다.

    인게임 상태
    → 커스터마이징 버튼 선택
    → 캐릭터 이동 제어 중지
    → 커스터마이징 UI 활성화
    → 아바타 파츠 선택
    → 선택 결과 반영
    → 인게임 복귀
    → 캐릭터 조작 복원

처음에는 화면을 켜고 끄는 정도로 생각했지만, 실제로는 입력, 카메라, UI, 캐릭터 상태가 같이 바뀌어야 했습니다.

이 부분을 작업하면서 UI 상호작용은 단순 버튼 이벤트가 아니라, 현재 플레이 상태를 바꾸는 작업이라는 점을 많이 느꼈습니다.

<br />

### 4-5. 로그인에서 인게임으로 이어지는 흐름

로그인 화면에서 인게임으로 넘어가는 흐름도 함께 작업했습니다.

프로토타입 단계였기 때문에 실제 서비스 수준의 인증 기능을 깊게 다루기보다는, 사용자가 로그인 화면을 거쳐 인게임 화면으로 진입하는 화면 흐름과 씬 전환을 맞추는 데 집중했습니다.

작업한 내용은 다음과 같습니다.

- 로그인 화면 UI에서 다음 화면으로 넘어가는 버튼 이벤트 연결
- 로딩 또는 화면 전환 프리팹 연결
- 인게임 진입 후 필요한 UI 상태 정리
- 이후 커스터마이징 화면으로 이어질 수 있도록 흐름 구성

이 부분은 기능 자체가 복잡하다기보다, 프로젝트 안의 여러 화면과 프리팹이 어떤 순서로 연결되는지 파악하는 데 도움이 됐습니다.

## 6. 구현하면서 배운 점

### 6-1. 커스터마이징은 데이터 정리가 중요하다

처음에는 파츠를 버튼에 직접 연결해서 바꾸면 될 것처럼 보였습니다.

하지만 의상 종류가 많아지고, 각 의상마다 적용 대상이나 숨겨야 하는 바디 파츠가 달라지면서 단순 연결 방식으로는 관리가 어려웠습니다.

그래서 아이템 ID, 카테고리, 착용 타입, 메시 렌더러, 숨김 파츠 같은 정보를 따로 관리하는 구조가 필요했습니다.

이 작업을 하면서 커스터마이징 기능에서는 “어떤 모델을 보여줄지”만큼이나 “그 모델을 어떤 기준으로 관리할지”가 중요하다는 걸 배웠습니다.

<br />

### 6-2. 캐릭터 조작은 카메라와 같이 봐야 한다

캐릭터 이동은 입력값만 처리하면 되는 기능처럼 보이지만, 실제로는 카메라 방향과 맞물려야 자연스럽게 느껴졌습니다.

카메라 기준 이동, 캐릭터 회전, 마우스 시점 조작이 서로 맞지 않으면 플레이어 입장에서는 조작이 바로 어색하게 느껴졌습니다.

이 작업을 통해 캐릭터 이동 기능은 단순 이동 로직이 아니라, 카메라와 함께 조정해야 하는 기능이라는 점을 알게 됐습니다.

<br />

### 6-3. 화면 전환은 UI만 바꾸는 일이 아니었다

커스터마이징 화면에 들어갈 때는 UI만 바뀌는 것이 아니라, 캐릭터 조작, 카메라, 캔버스, 인게임 UI 상태도 함께 바뀌어야 했습니다.

반대로 인게임으로 돌아올 때는 이 상태를 다시 원래대로 돌려야 했습니다.

이 경험을 통해 버튼 이벤트 하나를 연결하더라도, 실제로는 여러 오브젝트의 상태가 같이 바뀔 수 있다는 점을 배웠습니다.

<br />

### 6-4. 입사 초기 프로젝트로서의 의미

지금 기준으로 보면 더 깔끔하게 나눌 수 있는 부분도 있고, 구조적으로 아쉬운 부분도 있습니다.

하지만 당시에는 실무 프로젝트 안에서 캐릭터, UI, 카메라, 씬 전환이 어떻게 연결되는지 직접 다뤄볼 수 있었던 첫 경험에 가까웠습니다.

기능 하나를 구현하기 위해 코드만 보는 것이 아니라, 프리팹, 인스펙터 연결, UI 버튼 이벤트, 씬 안의 오브젝트 상태를 같이 확인해야 한다는 점을 이 프로젝트를 통해 많이 배웠습니다.

<br />

## 7. 포트폴리오 관점의 요약

이 프로젝트는 입사 초기 Unity 기반 3D 프로젝트에서 실제 기능 구현을 맡아 진행했던 작업입니다.

직접 담당한 범위는 다음과 같습니다.

- 캐릭터 이동 및 카메라 조작
- 캐릭터 커스터마이징
- UI 버튼 상호작용
- 커스터마이징 화면 전환
- 로그인 화면에서 인게임으로 이어지는 흐름

맵을 직접 제작한 것은 아니지만, 제작된 월드 안에서 캐릭터가 움직이고, 화면이 전환되고, 아바타 외형이 바뀌는 플레이 흐름을 구현했습니다.

이 프로젝트를 통해 Unity에서 캐릭터 조작, UI 상태 관리, 파츠 데이터 관리, 화면 전환이 어떻게 맞물리는지 실무적으로 경험할 수 있었습니다.

화려한 기능을 많이 넣은 프로젝트라기보다는, 입사 초기에 실제 프로젝트 구조를 익히고 기능 단위 구현을 맡아보며 Unity 3D 콘텐츠 개발의 기본 흐름을 배운 작업으로 정리할 수 있습니다.
